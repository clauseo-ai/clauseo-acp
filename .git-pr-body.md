## Task

sandbox: the setup exe carries full PE metadata and builds reproducibly (Defender's ML flag `Trojan:Win32/Bearfoos.A!ml` on the unsigned, metadata-free `clauseo-sandbox-setup.exe`; no behaviour change).

## What changed

- `crates/sandbox/build.rs`: on `*-windows-msvc` only, writes a `VERSIONINFO` `.rc` into `OUT_DIR` and links it into `clauseo-sandbox-setup` alone (`embed_resource::compile_for`). The values match the app's exe (tauri-build's resource), read from `crates/desktop/tauri.conf.json`: `ProductName` "Clauseo", `CompanyName` "Clauseo" (`bundle.publisher`), `LegalCopyright` (`bundle.copyright`), `FileVersion` and `ProductVersion` from `version` (release.yml checks that it equals `crates/desktop/Cargo.toml`'s). `FileDescription` is "Clauseo sandbox set-up", and `OriginalFilename` and `InternalName` are `clauseo-sandbox-setup.exe`. The `.rc` holds no manifest.
- `crates/sandbox/setup.manifest`, linked with `/MANIFESTINPUT`: the linker merges the app's `supportedOS` list (Windows 10/11, 8.1 and 8, as in `windows-app.manifest`) into its single `/MANIFESTUAC` manifest. Reproducibility: `/Brepro` and `/PDBALTPATH:%_PDB%`.
- `.github/scripts/sidecars.mjs`: the setup exe's build alone adds `--remap-path-prefix` for the repo, cargo home and target dir (`CARGO_ENCODED_RUSTFLAGS`, after the job's flags) and `SOURCE_DATE_EPOCH` from HEAD's commit time. A new `--setup-exe <triple>` mode builds only that exe. `.github/workflows/setup-exe-repro.yml` (manual `workflow_dispatch`) builds it twice from clean in `target/`, the release's build path, wiped between the builds, on both Windows targets. It compares the SHA-256s and uploads both exes on a mismatch.
- `embed-resource` 3.0.12 is a workspace and build dependency. It was already locked through tauri-winres, so Cargo.lock gains one edge and no new crate. `tests/setup_exe.rs` walks the resource directory and asserts `HIGH_ENTROPY_VA`, `DYNAMIC_BASE` and `NX_COMPAT` in DllCharacteristics.

## Deviations

- The build dependencies (`embed-resource`, `serde_json`) are not target-gated. A build script compiles for the host, so `cfg` can't follow the target; `build.rs` checks `TARGET` instead. Both crates were already in the tree.
- All values, the version included, come from `tauri.conf.json`, the file the app's exe takes its version from. They don't come from `crates/desktop/Cargo.toml`.
- Symbols and strip settings were left as they are: the setup exe inherits the release job's profile (`strip = true`, `lto`, `codegen-units = 1`, `panic = "abort"`, `CARGO_PROFILE_RELEASE_DEBUG=line-tables-only`, `SPLIT_DEBUGINFO=packed`, `-C force-frame-pointers=yes`), the same as `Clauseo.exe`. It is not packed.
- The exe is reproducible at the release's build path only, which is the goal: rebuilding a release commit in our CI gives the same hash. A different target dir gives a different exe. lld's PDB GUID, which the exe's debug directory holds, is a hash of the PDB, and the PDB holds absolute object paths and the link line. RUSTFLAGS' remaps also miss host proc macros and build scripts under `--target`: a first run with two target dirs differed on both targets, and a local link-line capture showed why.
- The repro proof is a manual workflow. Two cold LTO builds per target on every PR would be too slow.

## Not verified

- Everything that needs an msvc link: lld-link merging `/MANIFESTINPUT` with `/MANIFESTUAC`, `/Brepro`, `/PDBALTPATH`, and the new `setup_exe.rs` test. This Mac has no Windows SDK or `cargo xwin`. Windows CI runs the test.
